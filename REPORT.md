# Interview flow repair — 28 October 2026

The existing take-home demonstrates a Tavus CVI technical interview: Charlie observes candidate-led coding and design, answers requirements questions, and offers one conceptual hint only when asked. The repair preserves skips, earlier-stage revisits, quiet working time, the existing 55-minute technical cutoff and the hour-long schedule. It adds no scoring, cheating detection, ATS integration, interview mode or separate review agent. Slides and decks were not edited.

## Repaired boundaries

Phase tools now arrive as HTTPS callbacks with HMAC-SHA256 verification over the exact raw bytes, using Tavus's documented [tool delivery mechanism](https://docs.tavus.io/sections/conversational-video-interface/pal/llm-tool-delivery). The conversation identifies the interview and its pinned model card. Exact tool names and JSON schemas are checked. The action and its result/log commit together in PostgreSQL; matching retries reuse the result, changed arguments conflict. PostgreSQL row locks serialize tools to one active operation per interview, below the configured two-call maximum, across workers and restarts. Failed transactions release their locks and do not consume a slot. Browser phase/design/tool-completion endpoints fail closed.

An opaque, hashed ownership capability in an HttpOnly SameSite cookie protects candidate status, work, recording and telemetry. Mutations require an allowed Origin and CSRF header. Only the dedicated callback gateway is exposed through the temporary tunnel. PostgreSQL and candidate services bind to loopback. Credentials are read from local configuration, with no tracked database password default.

Candidate responses contain opened statements and saved work, without stored hints, rubrics, CV paths or system instructions. Private material is supplied only through signed server-to-Tavus tool responses. Workspace notices are public, small and within the documented 4 KB limit. The new Charlie card uses versioned tools and guardrails; older provisioned versions are not overwritten. Delivery binding records prevent new calls after an unbound tunnel/secret change. Runtime instructions are read from the interview's stored version.

## Execution and task usability

Python 3.12 and Node 24 run in disposable official images pinned by digest. Containers run as UID 65534, with no network, inherited API secrets or host mounts, dropped capabilities, no privilege escalation, a read-only base, one CPU, 256 MiB memory, 32 processes and bounded temporary storage. Source is sent over stdin into that isolated workspace. Execution has a five-second limit and a 64 KiB combined output limit enforced while reading. Timeout, overflow and cancellation remove the entire container. A periodic stale-container cleanup retries after worker/daemon failure. Docker failure never falls back to the host. The retained terminal endpoint uses the same runner and permits only exact supported solution-file commands.

The scraped dataset is retained, but new interviews select only problems 1/20/26 (Easy) and 3/11/49 (Medium). Both language scaffolds execute successfully without adding a solution. Run executes candidate-written tests; no judge, hidden tests or grading pipeline is claimed. Question/editor panes, examples, constraints and collapsible output remain; candidate chat, visible hints and the manual Python command box remain removed.

## Lifecycle, work and history

Setup is stored before creating a room. The returned identity is saved immediately, failed setup compensates with remote termination, and optional memory initialization cannot discard an otherwise usable session. Local end state and cleanup intent commit before remote termination; failures leave retryable intent for the server worker. The assessment clock starts once after media is joined with live microphone input, with a separate five-minute setup allowance. Server reconciliation enforces the existing schedule without a browser: introduction by 05:00, easy by 15:00, medium by 25:00, technical lock at 55:00 and completion at 60:00. The normal remote cap allows five minutes of setup plus sixty of assessment.

Refresh restores the owned interview and rejoins the existing room after a user gesture. Code, language, diagram and acknowledged revisions restore. Narrow transactional writes reject stale or conflicting saves; question-keyed boards restore on revisits. Explicit transitions request a bounded checkpoint before switching. Work accepted by the server freezes at 55:00; offline/late changes remain local and are identified as unacknowledged. Candidate snapshots and the linked interview remain transactionally consistent. These are saved snapshots, not every edit.

History is extractive: persisted phase openings, recent evicted reasoning and recent turns receive bounded space. Complete observed transcripts and saved code/board can be paged privately. Transcript reads stream database batches of 32 records rather than materializing all history; returned pages remain bounded. Restart reconstructs context from PostgreSQL. Updates do not themselves request speech, and the system does not run a separate silent reviewer. The local assembled extract has a 5,000-token ceiling; no claim is made about semantic summarization or Tavus's complete prompt size. Browser-observed speech is untrusted evidence and is not a verified transcript. Input/output token fields are estimates; unreported thinking tokens stay NULL and old telemetry is preserved.

## Recording

Recording captures shared-screen video only. Distinct MediaRecorder sessions remain distinct files. Segment identity, ordered chunks, checksums, size limits, duplicate checks and explicit acknowledgement/finalization replace raw append uploads. The bounded IndexedDB queue retains unacknowledged uploads and retries them. Interrupted segments are marked incomplete; the application does not present concatenated sessions as one valid video. Historical files are retained. This does not implement a full recording consent, retention or mixed-call recording workflow.

## Connection recovery follow-up — 29 October 2026

Added same-room retry after failed joins and unexpected leave events, with capped exponential delay and cancellation on deliberate leave. Initial restoration and media-ready acknowledgements retry, and browser API requests have explicit timeouts. Code and active-board snapshots retry from the local revision backup on recovery; a downloadable backup is available for unacknowledged changes. The server still rejects late or inactive-task writes, so these are never falsely marked as submitted.

Browser-observed transcript events are queued in IndexedDB and uploaded with stable UUIDs. A PostgreSQL receipt and the transcript insert commit atomically; an identical retry is acknowledged, and a conflicting retry is rejected. Events observed before the end can be uploaded after the call. The queue cannot recover messages the browser never received while disconnected, and the remote room must remain available for rejoining. The interview clock continues during outages. Live network interruptions were not tested against a billable Tavus room in this follow-up; automated tests simulate a dropped Daily connection, API/database errors, lost acknowledgements and queue recovery.

Follow-up validation passed 131 backend tests, including rollback-only PostgreSQL integration checks, and 27 frontend tests, plus strict type checks, lint and the production build. The outage tests include a real refused database connection and simulated browser/API failures; they do not constitute a live Tavus network-drop test. The temporary callback address was refreshed and rebound, and readiness verified that the callback responds before a new call is allowed. An ownership cookie is established before room creation so the browser can look up an existing interview if the creation response is lost.

## Tool delivery and closing follow-up — 29 October 2026

In the reported interview, Charlie said the next challenge had failed and opened it after a second request. The local callback logs show the successful later invocation; they do not establish whether the first invocation was attempted or where it failed. Tavus's system-tool inventory confirmed that `end_call` already exists. The prior v8 instructions limited it to repeated abuse and did not instruct a normal end after closing.

Charlie v9 instructs up to five retries after an initial failed stage, revisit or completion-marker invocation without prompting the candidate to retry. The gateway separately retries the same signed invocation after transient 5xx, 429 and transport failures, with five retries and bounded backoff; it does not retry permanent 4xx errors. Tool-call IDs and PostgreSQL transactions preserve idempotence. A reissued revisit that already opened the requested stage is also idempotent. The tool delivery timeout is 45 seconds for v9. Requests that never reach the gateway depend on Tavus's own delivery and the model following the retry instructions; five retries cannot be guaranteed by the gateway in that case.

After the candidate finishes, the v9 prompt asks for reflection on how the interview went and what they might improve, one question at a time, offers any remaining candidate Q&A, thanks them and says goodbye. An authenticated marker records completion intent, after which Charlie is instructed to use the built-in `end_call`. When Tavus reports the room ended, the background worker records the marked interview as completed. The model's conversational compliance and the timing of its farewell are not guaranteed; the hard 60-minute cutoff still applies.
